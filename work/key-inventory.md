## Claims that review refuted (name clashes and misnames, not duplicates)

- `cache_key(workspace, ::CollectionKey)::Union{Nothing,Int64}` and `cachekey(workspace, row)::String`: The claim itself says 'not one thing', and the code agrees, so this is not a duplicate. cache_key identifies a collection record. It covers every collection, including ones with no process row. It is minted from a counter in save! (Pipeline.jl:518-521) and is the primary and foreign key of the collection tables: collections keyed by collection_key (project_cache_domain.jl:316-317), parent_key and items.collection_key (Pipeline.jl:522, :493-498). cachekey identifies a catalog row of any kind: read:, item id, member:, collection: and computed (Pipeline.jl:141,158,386,455; Evaluate.jl:978). It keys computation_revisions and the stores (Evaluate.jl:198,408). For collections, the Int64 is the packed form of the collection's path, with one mapping held in Workspace.collection_keys (Pipeline.jl:488-490). collection_cachekey is the text form of that same path (Pipeline.jl:438-439). The naming collision is real: save! docstring 'its cache key' (Pipeline.jl:516-517), collection_cachekey docstring 'The cache key of the row' (Pipeline.jl:434-435), and a local hash also named cache_key (TreePanel.jl:126).

- `ItemKey` and `item_key (items.item_key, CacheDB.item_keys, item_key!)`: They serve different purposes, and one key could not serve both. ItemKey is a session-only position in Tree.items, never reused (Tree.jl:9-12). It also indexes Tree.given by position (Tree.jl:155, :166). Re-adding a removed id mints a new ItemKey (Tree.jl:145-149), and delete! drops it from item_ids (Tree.jl:165). So ItemKey identifies one occurrence of an item in this session's tree, and computed items get one too (Evaluate.jl:972). item_key is a persistent Int64 per item id. It is loaded from the items table at opening (project_cache_domain.jl:334-345), never released, and minted only on publish (:376-388). It keys the metadata wide tables by item_key (:328-333). If item_key were the tree index, the tree would lose the never-reused property that marks stale handles. If ItemKey were the cache key, it would change across sessions and on every re-add.

- `CollectionKey` and `collection_key Int64 (Workspace.collection_keys / cache_key)`: Not a duplicate. The two keys serve different purposes, and one Dict maps them. CollectionKey is the position of the collection in tree.collections for one session and is never reused (Tree.jl:14-17, :127-130). collection_key is the number that persists across sessions in the cache (Workspace.jl:270-272, Pipeline.jl:512-524). Workspace.collection_keys (Workspace.jl:271) maps CollectionKey to Int64, and restore! builds the reverse map (Pipeline.jl:486-491). This is the same split as ItemKey and item_key, which the task accepts. The difference in owner is real: Core mints the integer for collections (Pipeline.jl:518-520), and the cache mints it for items (item_key!). clear_cache_index! resets the item and source item counters but not next_collection_key (project_cache_domain.jl:770-783). Both points are inconsistencies in ownership, not two keys for one purpose.

- `CollectionPath` and `collection_cachekey text`: Refuted. The text is produced from the path by one function: collection_cachekey is "collection:" * join over path(workspace, key) (Pipeline.jl:437-438, path at Items.jl:92-94). It is the same identity, formatted with a single mapping and used in both places that need it (Pipeline.jl:386, :493). The text form is needed because the revision table and the stores are keyed by String, in a namespace shared with item ids, "read:" and "member:" keys and call_id texts. A Vector{Tuple{String,String}} cannot be that key without formatting. Side findings: (1) The id(::AbstractCollection) docstring (item_contract.jl:13-14) describes a one-way digest that no code builds; the only digest! calls are in CodeRevisions.jl:466 and :507. (2) The cache keeps a separate persisted identity for each collection: an Int64 collection_key minted by the workspace, with parent_key, identity and type_hex columns (project_cache_domain.jl:122-128; Pipeline.jl:516-519). That key is not derived from the path. Neither finding makes this pair a duplicate.

- `stored_key(T, id) String` and `MemoryStore key Tuple{Type,String}`: One address, (result type, store id), as the AbstractStore methods take it: write(store, id, item) and read(store, T, ids). Each store backend encodes it once, and the two encodings never live in the same store. MemoryStore uses the tuple in memory (MemoryStore.jl:12-35). DuckDBStore persists it as text through a single mapping, string(T, '\x1f', id) (DuckDBStore.jl:77-79), and uses that one string everywhere inside the store. payload_key (cache_buffer.jl:969), StoredShell.id (DuckDBStore.jl:3), TabularBodyBatch.id (cache_buffer.jl:716) and serialized_ids are names for that one string, not separate concepts. The name item_locations (cache_buffer.jl:744) is a misname for a map that holds any tabular result, not a duplicate.

- `store id parameter of the AbstractStore contract, and computation_revisions.id` and `id(item)`: Refuted as a duplicate: the two identify different things. The store and revision key is the cachekey of a row (Evaluate.jl:319-320, 493-497, 532-537). id(item) is the project's public id of an item (item_contract.jl:39-49). id(item) could not be the store key: an item's own row and its member row both return an item with the same id(item) but have different cachekeys (Pipeline.jl:158 vs :455), and computed results such as fit(a/1) are not items with that id. The facts in the claim do hold. The storage contract says the store keeps one item per item type and id (storage_contract.jl:5, 14). DuckDBStore passes the store key to reconstruct as the item's "stored id" (DuckDBStore.jl:141, 159; stage_contract.jl:246-248). So a rebuilt member-row result would get id "member:a/1" (deduced from reading the code, not run). This is a name collision and a contract mismatch, not two identifiers for one thing.

- `source_item_id(cache, key::Integer)::String` and `source_item_id(workspace, item::ItemKey)::Union{String,Nothing}`: These are two lookups that return the same identifier, the id of a source item. They are not two identifier concepts. The cache method inverts the packed surrogate source_item_key through its single mapping, cache.source_item_ids (project_cache_domain.jl:420-441). The Core method gives the source item of an item from TreeItem.source (Items.jl:177-182, Tree.jl:28-29). The name is shared and both are exported (DataBrowserCache.jl:74). That is an overloaded name with different inputs, not one thing identified twice.

- `OPEN_FILES` and `OPEN_STORES.paths`: Both registries key by the same identifier, the absolute file path (project_cache_domain.jl:268, DuckDBStore.jl:49). They hold different kinds of file and apply opposite rules. OPEN_FILES rejects a second open of a cache file, because two databases on one file corrupt its log (project_cache_domain.jl:235-238 and :269-273). OPEN_STORES returns the store that is already open, so that several item types share one results file (DuckDBStore.jl:21-22 and :48-52). One registry with one rule could not serve both purposes. The registries do not see each other, and the wide_columns DDL appears in both files (project_cache_domain.jl:459, DuckDBStore.jl:66). These are a missing guard and duplicated code, not two identifiers for one thing.

- `ROOT = CollectionKey(1)` and `empty CollectionPath()`: These are the session key and the path of one collection, the root. Every collection has both, with single mappings between them. CollectionPath is documented as what names a collection across sessions (Items.jl:55-60). path() leaves out ROOT, so the root's path is empty (Items.jl:92-94), and collection(workspace, []) returns ROOT (Items.jl:73-85). The browser uses each for its own purpose. It reads the workspace by key, as in label(workspace, ROOT) at TreePanel.jl:281. It holds paths in the persisted selection and scroll target (TreePanel.jl:242, 250, 272, 282). The other root spellings are the root in other key spaces, each with a defined mapping: nothing from cache_key (Pipeline.jl:534-535) and "" as TreeCollection.id (Tree.jl:122).

- `value_row(workspace, key)` and `member-else-own rule in bound_argument, input_rows(::Selection) and computation(workspace, key)`: The two rules have different purposes, and one rule could not serve both. bound_argument, input_rows and computation choose the row to depend on and wait for: the member row whenever one exists (Evaluate.jl:733-736, :747-748, :789-790). A dependency must name a fixed row, and push! rebinds when that structure changes (Evaluate.jl:957-967). value_row chooses the row whose result is usable now, by state: the member row if it is CURRENT, else the own row if it is CURRENT or STALE (Items.jl:221-226). It is used for metadata without waiting (Items.jl:212-214) and for when to save the label and metadata (Pipeline.jl:283). With the state rule, a dependency would bind to the own row and need rebinding. With the structural rule, the display would show nothing until the member row finishes. Both docstrings say 'latest value' for different things (Items.jl:218 vs Evaluate.jl:782-784), which is a vocabulary issue.

- `Window.active_item` and `VectorView.overlay_active`: Refuted. Neither is an identifier concept: both hold the same identifier, the public item id taken from Selection.id (Presentations.jl:151-152; VectorView.jl:132-134). They record different choices. active_item picks the one item that the Stack arrangement prepares and draws, and the other items are not drawn (Presentations.jl:152-153; VisualizerArrangements.jl:26, 62). overlay_active picks which item fills the numeric strip and statistics while all items stay plotted (VectorView.jl:71-78 tooltip; VectorOverlay.jl:14-17, 105-106). They are also owned by different layers on purpose. The browser owns presentation, and "The visualizer has no Stack/Grid contract" (State.jl:156). Overlay is Vector-specific (VectorOverlay.jl:1), and the visualizer cannot see window.active_item (WindowContext at State.jl:175-180). The shared idea of a focused item is a question of state design, not a duplicate identifier.

- `label(T::Type{<:AbstractDataItem})::Symbol (item kind)` and `label(item)::String (display name)`: Refuted as a duplicate: they identify different things. label(item) is the display name of one item, which can change after process (item_contract.jl:51-66; Pipeline.jl:284-287). label(T) is a fixed, per-type kind Symbol (item_contract.jl:69; carriers.jl:31). That Symbol is matched as a key in Recipes (stages.jl:177, 211, 253) and turned into display text only through kind_label (project_contract.jl:18; TreePanel.jl:77; InfoModal.jl:46). This is one generic function overloaded for two meanings, which is a naming issue. Its docstring "Display name for one item type" (item_contract.jl:68) does not match its use as a key. The places that hold the kind (ItemRecipe.kind, K, CollectionRecipe.members) store the same Symbol, not separate identifiers.

- `function_name(f)::String (Core)` and `function_name(f)::Symbol (DataBrowserPlots)`: These are two separate generic functions that share a name. They are applied to different functions and name different things. Core's names the function of a Computation: the start of call ids and cachekeys, the version seed and the Computed collection name (Evaluate.jl:913-918, :354, :970-971). It is overridden for Analysis to return 'fit' or 'aggregate', which is not nameof (AoG ext :756). Plots' names the metadata field of an aggregate function's value in a result group, such as :mean (aggregate.jl:13-15, :29, :40), and is applied to Aggregate.functions. Those are never the f of a Computation. The only things they share are nameof and the TODO about anonymous functions.

- `Tree.given slot (ItemKey.index)` and `Workspace.produced slot (Row.index)`: These identify different things. given holds the metadata that expand gave each item, by item position (Tree.jl:113, :156, :166). produced holds the metadata of the result of each row that gives an item or a collection, by row index (Workspace.jl:239-240, Pipeline.jl:278, :301, Evaluate.jl:440, :589). Items.jl:204-213 reads both, side by side, for different layers. They share a container type (MetadataColumns, Tree.jl:66-104) whose bare Integer index does not say which index space it is. That is a type-safety gap, not two keys for one thing.

- `CollectionRow.identity (a collection id)` and `ProjectCacheIdentity / CacheDB.identity (the cache file)`: Refuted: the claim itself says they are different things. CollectionRow.identity::String is the public id of one collection (project_cache_domain.jl:125, 133, 548). load_cache_index reads it back as id=row.identity (around :852), and restore! passes it to reconstruct(saved.type, saved.id, ...) (Pipeline.jl:484). CacheDB.identity::ProjectCacheIdentity is the project, source and path header of the whole cache file (project_cache_domain.jl:95, 173-191, 200, 308-310). This is one word used for two unrelated things in one file, a naming collision rather than a duplicate.

- `ProjectCacheIdentity.source_id (the workspace source)` and `source item id / source_item_key / source_key`: The claim itself names two different things. source_id identifies the whole source of one cache. It is checked against id(workspace.source) when the cache opens (project_cache_domain.jl:50-55; Pipeline.jl:476-477). Source item ids and source_item_key identify one source item each (project_cache_domain.jl:102-106, :410-424). SavedItem.source_key is that per-item key (:75-78). Only the word 'source' is shared.

- `delete_collection_metadata! / CacheDB.collection_process` and `collection_metadata table / collection_process_metadata table`: Not a duplicate pair. The claim itself says these are misnames, and the facts check out. delete_collection_metadata! deletes only from cache.collection_process (project_cache_domain.jl:669-677). The collection_metadata table is cleared by delete_collection_records! (:653-664). The field collection_process wraps the table collection_process_metadata (:333). source_item_metadata is keyed by item_key (:466-467 and :897). item_data and item_locations hold any tabular result (cache_buffer.jl:744, :764). Each name points to one thing, just the wrong-sounding one. So nothing is identified twice. These belong in the inventory as misnames.

- `itemkeys(input, state)` and `item_key!(cache, id)`: Refuted: different things, as the claim itself says. itemkeys resolves a window input to session ItemKeys, each a position in the tree (Windows.jl:14-20; Tree.jl:10-12). item_key! mints or resolves the cache's persisted Int64 surrogate of an item id (project_cache_domain.jl:375-387, minted at :509). natural_key is a text sort key (Items.jl:120-123). This is a name collision only. A separate pair that the inventory may want to check is ItemKey (a session-only Int32 tree index) versus item_key (a persisted Int64 cache surrogate): both are integer stand-ins for one item id.

- `label(visualizer)` and `PersistedWindow.visualizer (type name)`: They serve different purposes. label is a display name with a default of nameof(typeof) (visualizer_contract.jl:69), and a visualizer may override it, so it cannot reliably find the type again. PersistedWindow.visualizer is the persistence key: the bare type name written at save (Persistence.jl:189) and resolved by _visualizer_type, which compares String(nameof(V)) over prepare! methods (Persistence.jl:199-206). The two are equal only by default. The collision between packages with the same type name is a real flaw of the saved key, but that does not make the display label a duplicate of it.

- `id(::DirectorySource)` and `DirectorySource.root_path read directly by tag_root`: These serve different purposes. id(source) is the opaque identity of the source, which the cache checks against its header (Pipeline.jl:482-483). The tags file needs a folder on disk (Tags.jl:7-9). For DirectorySource the two values are equal only because its id is defined as root_path (directory_source.jl:84). Another source type can have an id that is no folder, so id could not replace the folder. The duck-typed hasproperty(source, :root_path) appears three times: Tags.jl:9, and the view file at Persistence.jl:122 and :317. It is a missing method for the folder of a source, not a second identity.
