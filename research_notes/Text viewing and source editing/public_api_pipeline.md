# Public API, text payloads, and the live Recipes workflow

## 1. What is supported through the public API today?

### Takeaway

`DataBrowserRecipes` is the package the user means by “DBRecips.” Its public registration API can recognize and read text with one callback, but this checkout cannot deliver a plain `String` as processed item data. The shortest working baseline for the actual SuperGaN folder is the built-in CSV recipe with `comment="#"`.

### Cited findings

- The umbrella re-exports API, Recipes, Sources, Core, Plots, and GUI. Recipes exports `define_project`, `register_item!`, `register_collection_analysis!`, and `register_csv!`, together with its concrete `Project`. [Umbrella](/Users/davide/code/Julia/DataBrowser-dev/src/DataBrowser.jl:7); [Recipes exports](/Users/davide/code/Julia/DataBrowser-dev/lib/DataBrowserRecipes/src/DataBrowserRecipes.jl:49).
- The recipe registration is `register_item!(project, [kind]; read, detect=Returns(true), expand=nothing, process=nothing, analyze=nothing, label=nothing, collection=nothing, id=nothing)`. `read` is the only required callback. Re-registering a named kind replaces the existing registration; narrower registrations should precede broad registrations because the first matching detector wins. [Registration](/Users/davide/code/Julia/DataBrowser-dev/lib/DataBrowserRecipes/src/registration.jl:44); [premade recipe ordering](/Users/davide/code/Julia/DataBrowser-dev/lib/DataBrowserRecipes/src/premade.jl:43).
- `SourceFile` is exported. Its `filepath` field is explicitly documented as the absolute path, and the current maintained example uses it in the reader. This field access is intentional public source usage, unlike reading a workspace's cache, catalog, or browser state. [Export](/Users/davide/code/Julia/DataBrowser-dev/lib/DataBrowserSources/src/DataBrowserSources.jl:10); [field contract](/Users/davide/code/Julia/DataBrowser-dev/lib/DataBrowserSources/src/directory_source.jl:65); [example](/Users/davide/code/Julia/DataBrowser-dev/examples/02_multi_entry_pipeline/project.jl:24).
- The built-in `register_csv!(project, [kind]; extensions, read_options, callbacks...)` recognizes extensions without regard to letter case, reads a `DataFrame`, and forwards other recipe callbacks. CSV is the only premade format recipe in this checkout. [CSV contract and implementation](/Users/davide/code/Julia/DataBrowser-dev/lib/DataBrowserRecipes/src/premade.jl:25).
- `read_item_data`, `materialize_items`, `modify_workspace!`, `query_items`, `select_items!`, `wait_workspace_idle!`, and workspace lifecycle/status operations are exported. `query_items(workspace)` returns stable ids for currently published items; this overload is sufficient for selecting an actual discovered item without constructing internal keys. [Core exports](/Users/davide/code/Julia/DataBrowser-dev/lib/DataBrowserCore/src/DataBrowserCore.jl:30); [ids overload](/Users/davide/code/Julia/DataBrowser-dev/lib/DataBrowserCore/src/Workspace/Operations.jl:604).
- `item_data(item)` is the common public payload accessor. Custom item types return themselves by default; Recipes supplies the accessor for its private carrier. Project consumers need not know or construct that carrier. [Item contract](/Users/davide/code/Julia/DataBrowser-dev/lib/DataBrowserAPI/src/item_contract.jl:83); [Recipes carrier accessor](/Users/davide/code/Julia/DataBrowser-dev/lib/DataBrowserRecipes/src/carriers.jl:54).
- The Table Inspector consumes Tables.jl payloads. It skips non-tabular payloads, uses `show` to format each table cell, and truncates that display to 90 characters. Therefore a one-column line table can be inspected today, but it is not a complete text viewer: strings are shown as values, long lines are truncated, and the interface is a grid. [Table preparation](/Users/davide/code/Julia/DataBrowser-dev/lib/DataBrowserGUI/src/TableModel.jl:107); [cell formatting](/Users/davide/code/Julia/DataBrowser-dev/lib/DataBrowserGUI/src/TableModel.jl:28); [Table Inspector](/Users/davide/code/Julia/DataBrowser-dev/lib/DataBrowserGUI/src/Gui/TableInspector.jl:113).
- Plain `String` processing is currently blocked by storage, before the Table Inspector has a chance to reject it. The cache passes every processed payload to its tabular payload store, which asks Tables.jl for columns. This is true with `cache=false`, which uses an in-memory DuckDB rather than a general arbitrary-value memory path. [Store contract](/Users/davide/code/Julia/DataBrowser-dev/lib/DataBrowserCache/src/project_cache_domain.jl:911); [tabular access](/Users/davide/code/Julia/DataBrowser-dev/lib/DataBrowserCache/src/cache_buffer.jl:878); [cache=false contract](/Users/davide/code/Julia/DataBrowser-dev/lib/DataBrowserCore/src/Workspace/Operations.jl:1).
- This conflicts with the stated vision that unsupported payloads remain uncached and get a basic inspector. That sentence describes intended behavior, not demonstrated current behavior. [Vision](/Users/davide/code/Julia/DataBrowser-dev/docs/vision.md:132); [current store](/Users/davide/code/Julia/DataBrowser-dev/lib/DataBrowserCache/src/project_cache_domain.jl:918).
- The exported plot API is `register_plot!(project, kind; label, setup, draw)`, whose callbacks receive `(workspace, items)` and `(workspace, items, figure)`. They receive processed `AbstractDataItem`s, not `(data, metadata)` vectors. Current example 02 still names these parameters `data, metadata` and tries to use the second as metadata; its plot callback is inconsistent with the actual public contract. Use the docstring and exported operation implementation for a new example. [Plot registration contract](/Users/davide/code/Julia/DataBrowser-dev/lib/DataBrowserPlots/src/plots.jl:76); [execution](/Users/davide/code/Julia/DataBrowser-dev/lib/DataBrowserPlots/src/DataBrowserPlots.jl:37); [inconsistent example](/Users/davide/code/Julia/DataBrowser-dev/examples/02_multi_entry_pipeline/project.jl:51).
- `GuiExtension` and `register_gui_extension!` exist inside the GUI implementation but are absent from both GUI export lists. Exporting them is explicitly unfinished in the roadmap. `embed` also exists in Plots but is absent from the Plots export list. Neither was used in this investigation. A project cannot add a supported generic text editor panel by reaching through `DataBrowser.Browser` today. [GUI exports](/Users/davide/code/Julia/DataBrowser-dev/lib/DataBrowserGUI/src/DataBrowserGUI.jl:7); [Browser exports](/Users/davide/code/Julia/DataBrowser-dev/lib/DataBrowserGUI/src/Browser.jl:21); [roadmap](/Users/davide/code/Julia/DataBrowser-dev/docs/roadmap.md:215); [Plots exports](/Users/davide/code/Julia/DataBrowser-dev/lib/DataBrowserPlots/src/DataBrowserPlots.jl:57).
- Generated documentation is stale in this checkout: its generated example calls removed `source_item_path` and `entries`, whereas maintained source uses documented `SourceFile.filepath` and `expand`. Generated files include internal implementation material too, so their presence in the book is not evidence of a public extension hook. [Generated example](/Users/davide/code/Julia/DataBrowser-dev/docs/generated/code/examples/02_multi_entry_pipeline/project.md:34); [maintained example](/Users/davide/code/Julia/DataBrowser-dev/examples/02_multi_entry_pipeline/project.jl:24).

| Capability | Existing public interface | Remaining feature |
| --- | --- | --- |
| Recognize ordinary text files | `register_item!` detector, `label(source_item)` | Premade text recipe and a policy for text-like filenames/content |
| Read directory text | Documented `SourceFile.filepath`; ordinary Julia `read` | Encoding choice and binary/huge-file handling in a shipped recipe |
| Deliver a processed string | No working route verified; Tables.jl storage rejects `String` | General supported text payload or explicit arbitrary-value resident fallback |
| Inspect table-like text | A NamedTuple of vector columns is an ordinary recipe payload | Complete selectable text, long-line display, line navigation, search, wrapping |
| View a derived text value | Reader/process callbacks may produce it, subject to payload-storage support | Generic text capability and visualizer |
| View raw source bytes before parsing | Public source discovery exists; no workspace preview operation | Source-preview request independent of semantic read/expand success |
| Choose an intermediate pipeline result | No `stage` argument on public item-data access | Shared result selection, defined in roadmap 0.14.0 |
| Add a generic panel/editor | No exported GUI extension/window surface today | Documented public host surface, without browser-state access |
| Refresh an existing workspace after code changes | `modify_workspace!(workspace; rebuild=true)` | Finer public invalidation and code/project refresh operations |

### Inferences

- A text viewer should consume a suitable payload rather than demand a special recipe carrier or item subtype. `AbstractString` is a natural first payload capability, but the current processing/storage path must support it before this is useful.
- A short-term line-table recipe is useful for diagnosis only. Treating text as a table to satisfy storage is an implementation accommodation, not the desired model or the user's “shortest code” outcome.
- A generic source preview needs its own request semantics. Calling the project's semantic `read` merely to show raw file text would prevent inspection of malformed CSVs, unsupported files, and source files whose parser fails.

### Gaps

- No public text viewer, general scalar inspector, source editor, source preview selector, public project-code document API, or currently exported generic GUI extension surface was found. The roadmap's generic inspectors and pipeline inspection are unchecked. [Core visualizers](/Users/davide/code/Julia/DataBrowser-dev/docs/roadmap.md:486); [pipeline inspection](/Users/davide/code/Julia/DataBrowser-dev/docs/roadmap.md:524).

## 2. What pipeline design does text viewing need?

### Takeaway

The existing public data-access path returns a processed item and eventually the latest collection version. Source preview and result selection should be public workspace operations, leaving the text viewer unaware of job, cache, and stage details.

### Cited findings

- The typed contract is `read(project, source, source_item)` → `expand(project, source_item, loaded)` → item `process` → item `analyze` → collection processing/analysis. `read` is the only stage receiving the source. It returns an `AbstractDataItem` for a single logical item, or arbitrary loaded content for `expand`; `expand` must preserve its cached input for possible reuse. [Stage contract](/Users/davide/code/Julia/DataBrowser-dev/lib/DataBrowserAPI/src/stage_contract.jl:22); [architecture](/Users/davide/code/Julia/DataBrowser-dev/docs/ARCHITECTURE.md:151).
- Recipes `read` runs detection and invokes the reader. No matching registration expands into zero items. Thus a directory containing PNG and CSV files does not automatically offer an image/text preview for everything: files without a matching recipe produce no browsable data items after discovery completes. [Recipes routing](/Users/davide/code/Julia/DataBrowser-dev/lib/DataBrowserRecipes/src/stages.jl:134); [no-match expansion](/Users/davide/code/Julia/DataBrowser-dev/lib/DataBrowserRecipes/src/stages.jl:151).
- The tree temporarily displays unread source items as gray rows. Clicking them requests source reading first. This is processing prioritization, not source-value visualization. [Tree behavior](/Users/davide/code/Julia/DataBrowser-dev/lib/DataBrowserGUI/src/Gui/TreePanel.jl:315); [architecture](/Users/davide/code/Julia/DataBrowser-dev/docs/ARCHITECTURE.md:170).
- DirectorySource excludes dotfiles and app sidecars `metadata.txt`, `tags.txt`, `notes.txt`, `layout.txt`, and `databrowser.toml` from candidate data files. A first text experiment named `notes.txt` therefore correctly produced no text data item; the diagnostic was repeated with `sample.txt`. [Discovery exclusions](/Users/davide/code/Julia/DataBrowser-dev/lib/DataBrowserSources/src/directory_source.jl:144).
- `materialize_items(workspace, items)` waits for item `process`, requests item `analyze`, and requests ancestor collection processing/analysis without waiting for those collections. A later call can return a collection's newer version. Failed items throw. `read_item_data` extracts `item_data` from those materialized items. Neither operation offers a source/raw/intermediate stage option. [Materialization contract](/Users/davide/code/Julia/DataBrowser-dev/lib/DataBrowserCore/src/Workspace/DataAccess.jl:1); [payload access](/Users/davide/code/Julia/DataBrowser-dev/lib/DataBrowserCore/src/Workspace/DataAccess.jl:111).
- Source-read values live in a bounded memory cache and are not persisted to disk by default. Eviction can require rereading even though reading previously succeeded. This is an internal storage observation, not an operation available to project code. [Read-stage storage contract](/Users/davide/code/Julia/DataBrowser-dev/lib/DataBrowserCache/src/source_stages.jl:20).
- The roadmap already specifies a shared application API for `read`, `expand`, `process`, `analyze`, collection `process`, and collection `analyze`; source siblings should coalesce, collection members should group, metadata should appear beside the corresponding data, and cached/uncached intermediates need explicit memory bounds. [Roadmap 0.14.0](/Users/davide/code/Julia/DataBrowser-dev/docs/roadmap.md:524).
- Exact stage-output references, metadata by producing stage, and coordinated publication are still unfinished cache work. A viewer should not claim a precise historical result based solely on the current item id or current merged metadata. [Remaining cache work](/Users/davide/code/Julia/DataBrowser-dev/docs/roadmap.md:147).
- DataBrowser's public text recipe interface currently delegates file decoding to the reader callback; the sole premade recipe delegates CSV parsing options to CSV.jl. No common encoding or bytes/text conversion policy was found. [Registration](/Users/davide/code/Julia/DataBrowser-dev/lib/DataBrowserRecipes/src/registration.jl:63); [CSV read options](/Users/davide/code/Julia/DataBrowser-dev/lib/DataBrowserRecipes/src/premade.jl:25).

### Inferences

- Keep two choices separate in the user interface: **which value** to inspect (source, read result, expanded item, processed item, collection result) and **how** to inspect it (text, table, plot). Choosing text should not silently rerun every later stage.
- A source preview should be able to show a known source item before its parser succeeds, without inserting a fake data item or changing the project's interpretation. Its payload should identify whether it is complete or truncated and carry a source revision/change token.
- Initial supported text should state its decoding rule, preserve newline information when displaying source code, report invalid encoding instead of silently changing bytes, and handle NUL/binary-looking content explicitly. These are design requirements, not current functionality.
- Large-file handling needs more than a renderer that clips off-screen lines. `read(file, String)` reads the whole file; `readlines` allocates line strings; current item materialization waits synchronously. A bounded preview/windowed content provider can be a later public capability without making ordinary small `String` values complicated.
- Read-only data text and editable project code should share rendering components when useful but have different identity and persistence. A derived `String` has no necessary source file; a project-code document needs a real writable path, dirty buffer, saved revision, and explicit evaluation/application. Saving a derived value should not silently overwrite the source that produced it.
- For a source item owned by a database, archive, stream, or custom source, a `filepath` need not exist. Generic text viewing should therefore accept returned text/bytes/document content rather than call a file field. Filepath use is suitable for the current explicit DirectorySource experiment only.

### Gaps

- The roadmap does not yet define public operation names and return shapes for result selection or source preview. Do not present invented `read_item_data(...; stage=...)`, `read_source_data`, `open_text!`, `refresh!`, or `register_text!` calls as runnable code.
- Whether source preview is a source capability, a loader-independent file utility, or a first public result selection needs a product decision. The requirement to inspect failed/unrecognized input should be preserved whichever interface is chosen.

## 3. Verified no-restart workflow and actual SuperGaN evidence

### Takeaway

The actual SuperGaN folder was opened directly and its 59 CSV files were discovered through the public built-in recipe. A named analyzer was loaded with `Revise.includet`, added to the live project, then changed by saving its file and running `Revise.revise(throw=true)`. The same browser and workspace stayed open throughout. The original recipe was restored for a baseline screenshot, then the tested analyzer was added again for a second screenshot. The app remains open in the analyzed state.

### Runnable initial commands

These are seven top-level statements, including the two imports, one project definition, one recipe registration, one data-directory assignment, one workspace opening, and one browser opening. There is one recipe-registration statement and no custom item type or helper constructor:

```julia
using Revise
using DataBrowser
project = define_project("SuperGaN")
register_csv!(project; read_options=(comment="#",))
data = "/Users/davide/Library/CloudStorage/OneDrive-LundUniversity/projects/Lind/SuperGaN/data"
workspace = open_workspace(project, data; cache=false)
```

### Inferences

- The shortest explicit update for a newly introduced callback is: define the function, register it, then call `modify_workspace!(workspace; rebuild=true)`. Once a named function is registered, later method edits need the rebuild but not registration again.
- Evaluate `includet` and callback registration/rebuild in separate REPL evaluations. After saving a tracked file, evaluate `Revise.revise(throw=true)` and the rebuild separately as well. The first research attempt put dynamic file loading and registration/rebuild inside one `begin` block and failed with a method-too-new error (world 39369 versus 39371); the next REPL evaluation rebuilt successfully. This establishes the requested line-by-line workflow, not a claim that arbitrary scripts performing dynamic inclusion see new methods inside the same evaluation.
- In VSCode, evaluate the function definition and registration through the existing REPL session. A file containing named methods can be tracked with Revise, but registration statements still need evaluation when adding/replacing callback wiring. A saved file is not the same as a loaded method, and a loaded method is not the same as recomputed cached data.
- The initial browser is a data-item tree, not a file explorer or IDE. Without a matching registration, a PNG or unknown file does not become an inspectable data item. This is the first user-visible gap the source/text viewer should address.

### Gaps

- Actual screenshots are saved as [supergan-baseline.png](</Users/davide/code/Julia/DataBrowser-dev/research_notes/Text viewing and source editing/supergan-baseline.png>) and [supergan-analysis.png](</Users/davide/code/Julia/DataBrowser-dev/research_notes/Text viewing and source editing/supergan-analysis.png>). The second visibly shows `points = 199` and `maximum_current_uA = 6.1025` in the Information Panel. Both show the actual DataBrowser window only; its Table Inspector remains closed by default. A research-only public CoreGraphics capture ran inside the owning Julia process, verified the specific window's owner, and captured that window without changing Screen Recording permissions. [Capture commands and verification](</Users/davide/code/Julia/DataBrowser-dev/research_notes/Text viewing and source editing/supergan-evidence.md>).
- Live plot callback method changes in a long-running browser render task were not verified. The worker rebuild proof must not be generalized into a claim that every GUI callback sees revised methods automatically.
